# 功能候选清单

聊天界面卡片优化的调研中未采纳/待评估的建议，记录上下文以备后续决策。

---

## P2 — 候选卡一步化（暂定，用户不反对但未拍板）

**现状**：候选卡（candidate_card）选定食物后，后端必定再生成一张 portion_card 让用户二选份量——两步串行、两次点击、两次往返（`pending.ts` food_choice 分支）。2026-07-03 体检时发现这曾与 AI_PARSING_SPEC §4 旧文冲突，现规范已改为如实描述两步现状。

**建议**：候选卡每个选项点击 = 按默认档（chosen_label，通常中份）直接入库，卡片原地变成 record_card，卡上带「小/中/大」档位 chips + 撤销。选错档位从"事前必答题"变成"事后一键改"。

**收益**：歧义食物的录入点击减半；配合已有学习闭环（改档即学习信号）。

**风险/待决**：默认档错误率若高，"先记后改"会让不看卡的用户积累脏数据；需决定 record_card 是否长出档位 chips（卡片形态变化）。

## P1 — ChatCard 共享基组件

**现状**：`RecordCard` 与 `ExerciseCard` 约 80 行重复代码（badge 行、主行、热量块、撤销区域的结构和样式几乎完全相同）。

**建议**：提取一个 `ChatCard` 基组件，统一 badge 图标 + 主信息行 + 热量数字 + 可选撤销行 的骨架。两个卡片只需注入内容差异（食物名+宏量素 vs 运动类型+时长）。

**不做的代价**：后续改卡片全局样式需改两处，新增卡片类型需再抄一遍。

---

## P3 — 滑动手势撤销

**现状**：撤销功能通过卡片右下角的可见"撤销"按钮 + "已撤销"文字实现，占用卡片第二行空间。

**建议**：用 iOS 标准左滑手势（`Swipeable` / `react-native-gesture-handler`）触发撤销，与系统邮件/消息的交互一致。撤销后卡片可直接消失或变灰。

**收益**：去掉撤销行让卡片更紧凑；交互更自然。

**风险**：与 FlatList 的横向滚动可能冲突；Android 上手势预期不同。

---

## P3 — 同餐食物分组

**现状**：用户连续记录同一餐（如午餐）的多条食物时，每条独立展示为一张 RecordCard。

**建议**：连续同餐的 RecordCard 合并为一张分组卡片，类似：
```
✓ 午餐 · 3 项          720 kcal
  ● 蛋白 45g  ● 脂肪 12g  ● 碳水 80g
```

**收益**：大幅减少卡片数量，信息密度更高。

**复杂度**：需要处理分组内单条撤销、分组折叠/展开、跨餐边界判定。

**搁置原因（2026-07-03 决策）**：功能本身认可，但**撤销/修改的交互设计未想清楚**——合并成一张卡后，"撤销第 2 项"、"把第 3 项换成大份"如何在分组卡上表达（逐项展开操作？长按进编辑态？modify 意图指代 ref 如何映射到组内项？）没有满意方案。想清楚这一层再启动。

## 气泡风格卡片

**现状**：AI 文本气泡有 `borderBottomLeftRadius: 6` 尖角 + `maxWidth: 78%`，卡片则是独立圆角矩形 `width: 90%` / `maxWidth: 100%`，视觉上卡片不像"AI 说的话"。

**建议**：卡片继承气泡的尖角 + 宽度约束，更像对话流的一部分而非嵌入的独立组件。

**风险**：卡片内容比纯文本复杂，过窄可能挤压宏量素行；需要实际测试各卡片的可读性。

---

## QueryCard 顶部常驻

**现状**：`QueryCard`（今日剩余热量）作为一条聊天消息插入对话流中，随滚动消失。

**建议**：将剩余热量提取为聊天页顶部固定横条（sticky header / 绝对定位），始终可见。用户随时能扫一眼今天还能吃多少。

**收益**：不用滚回顶部查热量余额。

**权衡**：占用屏幕空间，可能与导航栏冲突；不再是"对话"的一部分，交互模型变化较大。
