# 功能候选清单

聊天界面卡片优化的调研中未采纳/待评估的建议，记录上下文以备后续决策。

---

## P2 — 候选卡一步化（暂定，用户不反对但未拍板）

**现状**：候选卡（candidate_card）选定食物后，后端必定再生成一张 portion_card 让用户二选份量——两步串行、两次点击、两次往返（`pending.ts` food_choice 分支）。2026-07-03 体检时发现这曾与 AI_PARSING_SPEC §4 旧文冲突，现规范已改为如实描述两步现状。

**建议**：候选卡每个选项点击 = 按默认档（chosen_label，通常中份）直接入库，卡片原地变成 record_card，卡上带「小/中/大」档位 chips + 撤销。选错档位从"事前必答题"变成"事后一键改"。

**收益**：歧义食物的录入点击减半；配合已有学习闭环（改档即学习信号）。

**风险/待决**：默认档错误率若高，"先记后改"会让不看卡的用户积累脏数据；需决定 record_card 是否长出档位 chips（卡片形态变化）。

## P1 — ChatCard 共享基组件

**现状**：`RecordCard` 与 `ExerciseCard` 约 80 行重复代码（badge 行、主行、热量块、撤销区域的结构和样式几乎完全相同）。

**建议**：提取一个 `ChatCard` 基组件，统一 badge 图标 + 主信息行 + 热量数字 + 可选撤销行 的骨架。两个卡片只需注入内容差异（食物名+宏量素 vs 运动类型+时长）。

**不做的代价**：后续改卡片全局样式需改两处，新增卡片类型需再抄一遍。

---

## P3 — 滑动手势撤销

**现状**：撤销功能通过卡片右下角的可见"撤销"按钮 + "已撤销"文字实现，占用卡片第二行空间。

**建议**：用 iOS 标准左滑手势（`Swipeable` / `react-native-gesture-handler`）触发撤销，与系统邮件/消息的交互一致。撤销后卡片可直接消失或变灰。

**收益**：去掉撤销行让卡片更紧凑；交互更自然。

**风险**：与 FlatList 的横向滚动可能冲突；Android 上手势预期不同。

## P3 — 同餐食物分组【已立项 T46–T48，归档】

**结局（2026-07-04 决策）**：立项为餐食卡 G 轨（T46 后端一餐一卡 + T47 原地刷新 + T48 MealCard 组件）。当时的搁置原因（合并卡上撤销/修改怎么表达）被新交互方案解开：**修改全部走自然语言**（现有 modify 意图，无需在卡上发明编辑态），卡片只负责原地刷新，改完回复"已修改，营养数据已更新"。

三个关键决策：
1. **单食材也统一用 meal_card**——全项目只有一种饮食卡形态，续报"还有粽子"同卡长出第二项；
2. **分组 = 日期 + 餐次**（与 food_record / Today 页口径一致）。评估过时间窗口聚类，否掉：任何 N 分钟都有反例（本质是想用时间模拟"餐"这个语义，而语义已有 meal_type），且它解决不了真痛点；
3. **卡片跟随机制解决"卡片被淹没"**——真痛点不是分组规则，而是卡片停在诞生位置，聊天一多就沉底，"原地更新"变成"看不见的地方更新"。跟随 = 内容每次变更把同一条 chat_message 的 created_at 刷新，卡片浮到聊天流末尾：不是新消息、一餐永远一张卡、永远在眼前。加餐一天多次合一张卡的体验问题也随之消解（变成跟着走的流水卡）。

明细与总计**读取时从 food_record 实时组装**（payload 只存组装键），贴合铁律 2/3：卡片永不过期，删改撤销自动反映。

## 气泡风格卡片

**现状**：AI 文本气泡有 `borderBottomLeftRadius: 6` 尖角 + `maxWidth: 78%`，卡片则是独立圆角矩形 `width: 90%` / `maxWidth: 100%`，视觉上卡片不像"AI 说的话"。

**建议**：卡片继承气泡的尖角 + 宽度约束，更像对话流的一部分而非嵌入的独立组件。

**风险**：卡片内容比纯文本复杂，过窄可能挤压宏量素行；需要实际测试各卡片的可读性。

## QueryCard 顶部常驻

**现状**：`QueryCard`（今日剩余热量）作为一条聊天消息插入对话流中，随滚动消失。

**建议**：将剩余热量提取为聊天页顶部固定横条（sticky header / 绝对定位），始终可见。用户随时能扫一眼今天还能吃多少。

**收益**：不用滚回顶部查热量余额。

**权衡**：占用屏幕空间，可能与导航栏冲突；不再是"对话"的一部分，交互模型变化较大。

## 架构候选 — AI 主动调用查询工具（agentic tool calling）【已按变体落地，归档】

**结局（2026-07-04，T44）**：以**查询计划**变体落地——不是"给 AI 挂工具自由调用"的拉模型，而是中间态：AI 只输出一份受限的结构化查询单（QueryPlan），后端 zod 校验后确定性执行 SQL。协议与安全边界见 `AI_PARSING_SPEC §11`。当时的四条反对理由全部化解：恒定一次 flash 调用（非循环）；计划本身是结构化输出可被 eval 断言；计划里没有 user_id 字段、三表白名单只读；分工哲学与铁律4（AI 归一化、后端确定性执行）一脉相承。T43 的正则老路已同任务删除。

**仍然不做的部分**：真 agentic 工具循环（AI 自己决定调几次、循环到满意）。**触发条件保留在案**：当"计划 schema 表达不了的问法"高频出现（观察 trace 里 `meta.stage="query_plan"` 的失败率），尤其是多步依赖查询（"比上周吃得多的那天我吃了啥"），再重新评估。

<details><summary>原始讨论记录（2026-07-04 立项时）</summary>

**现状**：全项目走"推"模型——每轮对话前后端先拼好上下文（L0/L1/L2 记忆包、周月聚合等）喂给 AI，AI 只管理解文本、生成回复，不自己决定查什么、调什么。2026-07-04 讨论起因：用户问"昨天具体吃了什么"，`query.ts` 的 `fetchDayData` 只查了当日总量聚合，没查具体食物条目，AI 如实回答"没有更细的数据"——这是功能没做全，不是靠 AI 自己查就能绕开的架构缺陷。

**候选方向**："拉"模型——给 AI 挂只读查询工具（如 `query_food_records(date_range)`），让它自己判断要不要调、调几次，覆盖开放式统计问题（如"这个月吃了几次红烧肉"），不用后端穷举每种可能的聚合维度。

**当时评估的反对理由**：延迟/成本（至少两轮 LLM 往返）；可测性（AI 调不调工具是新的不确定性）；安全边界（user_id 不能信任 AI 填）；与"少让 AI 自由发挥、多让后端确定性兜底"哲学不一致。

</details>
