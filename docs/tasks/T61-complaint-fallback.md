# T61 — 产品投诉分流：「为啥不能用了」不再被「超出服务范围」怼回

**状态**：⬜未开始

**目标**：用户反馈 App 故障/不满（「为啥不能用了」「怎么又闪退」「登录不上」）时，给出承认 + 安抚 + 「会记录反馈」的回应，而不是套用「这个问题超出我的服务范围啦～」的 off-topic 模板——那句话面对故障投诉观感极差。

**依赖**：无。碰 chat 意图的回复 prompt（`ai/answers.ts`）。
**关注文档**：`AI_PARSING_SPEC.md`（意图路由——本任务**不加新意图**，只分流话术）。

## 背景（2026-07-09 真机，账号 outoftoken）

19:41 用户当晚第一句「**为啥不能用了**」，AI 回「这个问题超出我的服务范围啦～我只能帮你解答饮食、营养和运动相关的问题 💪」。用户在报障，得到的是拒答模板。（后端 14:45–19:41 全库零 AiTrace，无法确认是否真宕过——若服务挂了本来也不会有 trace；故障本身另查，本任务只修话术。）

## 设计要点

### A. chat 回复 prompt 的 off-topic 分支细分
现有「超出服务范围」话术保留给真正的无关请求（写作文/写代码/聊八卦）。新增分支：消息是**对本 App 的故障反馈或抱怨**（不能用、打不开、闪退、卡死、登录不上、数据丢了、又出 bug）时：
- 先承认收到（「刚才应该是出了点问题」），不狡辩、不装没事；
- 说明反馈会被记录关注；
- 如功能现在正常，自然引导继续（「现在应该恢复了，你刚要记什么可以再发我」）。
- **不编造故障原因**（配合 T58 系统事实原则：不知道就不知道）。

### B. 保持最小改动
只动 prompt 分支与话术，不新增意图枚举、不建 feedback 表、不做工单系统。真要沉淀反馈，人工看 AiTrace 即可。

## 验收
1. 发「为啥不能用了」「怎么又闪退了」→ 承认 + 安抚式回应，无「超出服务范围」模板。
2. 发「帮我写个作文」→ 仍走 off-topic 拒答。
3. `npm run eval` 全绿（干净端口，别打 :9300），建议为 1/2 各加一条用例。
