# T63 — 对话审计工具：明示信号采纳率扫描（对话精度 R2）

**状态**：✅完成（2026-07-27）

**验收记录**：`npm run audit` 可跑（支持 `--days N` / `--user X`）；`tsc --noEmit` 零错误；首次全量扫描 443 条真实消息，捞出 7 类可疑信号共 24 条，人工复核后确认 5 类真实缺陷，其中 **2 类（宏量素修改静默改错、一句话跨两餐）此前无人投诉、不在任何任务里，已静默存在 3 周**——工具立刻证明了自身价值。

**目标**：把"用户明说了但系统没照做"这类失败的发现路径，从「用户发火 → 立项 → 修」换成「跑一遍就知道」。零 LLM 调用、纯确定性判定、只读。

**依赖**：无。
**关注文档**：本文件即工具说明；抽取器规则的唯一定义处是 `src/services/explicit-signals.ts` 的注释。

## 为什么做这个（立项背景）

2026-07-27 复盘时用户问："拆东墙补西墙的做法什么时候是个头？"

扫数据后结论是**补上的墙没塌**：T42 修复后 88/88 全对，T53 修复后 1/1 对，日期词 5 条错误全部集中在 T62 上线当天、之后零复发。所以过去 27 个对话任务不是"按下葫芦浮起瓢"。

真正的问题是**每一类 bug 都要等用户骂了才被发现**。而"用户明说了但系统没照做"这一类，**天然可以机器判定**——用户说 80 卡、落库不是 80，不需要任何 AI 就能断言。于是有了这个工具。

## 已落地的设计

### 抽取器 `src/services/explicit-signals.ts`（共享，勿复制）
明示信号 = 用户原话里明确说出口、无需推断的值：
- `calories` 显式热量、`weights` 显式重量/容量（斤自动×500）
- `dateOffset` 相对日期词、`meals` 餐次词命中（带位置 + 是否"时段词+的"定语用法）
- `instructions` 指令动词+数值、`ingredients` 主料名
- `derivedRequest` **派生值请求标志**——"不去芯是340克，你算下去芯的"、"纯肉不算骨头"这类，用户要的是推算值而非字面值，校验必须跳过（实测这是最大误报来源）

**放在 `src/services/` 而不是 `scripts/` 是刻意的**：后续 A 轨要在解析链路做运行时校验，必须与审计共用同一份定义。两份定义必然漂移——T59 已经在 QUICK/FULL 提取 prompt 上栽过一次。

### 报告器 `scripts/audit.ts`（`npm run audit`）
- A 轨：7 类明示信号的"可判定数 / 可疑数 / 可疑率"+ 明细
- B 轨：食物库健康度——条目来源分布、真实记录命中估算条目的占比、用户覆盖热量的食物按中位偏差排序、属性后缀重复叠加的脏条目
- 只收 `canonical` 不收 `raw` 判主料覆盖（`raw` 是用户原话回显，用它判必然全绿——首版就栽在这）
- 覆盖统计排除 `eval_*` 账号（eval 用例会反复触发同一条覆盖，不滤会淹没真实样本）

### 刻意的设计约束
**输出是可疑清单，不是判决。** 实测误报约 20%，两大来源：派生值请求、同义归一（"鸡蛋"→"水煮蛋"是正常归一不是丢主料）。已内置抑制规则与同义词表，但**必须人工复核后再立项**——工具的价值是把发现成本从"用户受苦几周"降到"一分钟扫一遍"，不是取代判断。
