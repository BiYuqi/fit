# T39 — 回答质量：chat/query/discuss 升 pro + 人设提示词（对话智能）

**状态**：⬜待办

**目标**：面向用户的**文字回复**（answerChat / answerQuery / answerDiscuss）从"机械、单薄"升级为"专业、有人味"。解析（parse）不动，仍是 flash 主力 + 低置信升 pro。
**依赖**：无硬依赖（建议在 T36/T37 之后做，上下文补全后提示词才有料可用）　**关注文档**：AI_PARSING_SPEC §1、CALORIE_ENGINE（口径引用）

## 背景（为什么会有这个任务）

2026-07-03 体检：解析失败会升 pro，但直接面向用户的三个回答调用**永远走 flash**，且 system prompt 只有一两句话——无人设、无格式约束、无示例。"AI 感/机械感"大半来自这里。这三类调用频次远低于 parse、质量敏感，升 pro 成本可控（token 计量已按 purpose 分桶，上线后可直接对账）。

**铁律 1 红线**：升级提示词时必须保留"数字只来自上下文、AI 不自算热量"的约束——文风可以活，账不能算。

**只读路径禁止谎称操作（2026-07-03 真实案例，最高优先）**：用户 outoftoken 说"记录成180kcal"，被路由到 discuss（只读），flash 回复"已更新【葱花饼】热力为 180kcal"——数据库根本没动（仍 267），下一轮"今晚都吃了啥"回答 267 当场穿帮。chat/query/discuss 是只读路径，三个 prompt 必须硬性写明：**绝不声称"已记录/已更新/已修改/已删除"任何数据；做不到的动作要明说做不到，并引导用户用能触发 modify 的说法**（配 few-shot 反例）。

## 做什么（指引，不限定实现细节）

- `ai/answers.ts` 三个函数模型改为 `deepseek-v4-pro`（recordTokenUsage 的 model 参数同步）。
- 重写三个 system prompt，共享一段人设基底 + 各自职责段：
  - **人设基底**：专业但不说教的减脂教练；简洁中文（手机气泡，默认 ≤3 句，用户追问再展开）；所有数字**只引用上下文/记录详情，绝不自行计算或推算热量**；上下文里没有的数据要坦白说"没记录"，不编造。
  - **answerChat**：保留超范围拒答话术；结合【今日进度】【本周】给建议时引用真实数字。
  - **answerQuery**：回答对应【今日进度】/【近3日】/【本周】【本月】（T36 后可用）；问到无数据的日期明确说无记录。
  - **answerDiscuss**：保留现有偏差校准说明与"改成X克"引导（T31 逻辑不动），只做语气与结构优化。
- record/modify 的模板回复**不动**（确定性数字属于后端，铁律 1）。
- 可选：每个 prompt 附 1~2 个 few-shot 示例（好/坏对比），控制 token 增量。
- 兜底文案顺手改掉不自然的（answerChat 失败兜底"好的"→ 中性的"我没太明白，能换个说法吗？"）。

## 验收

- 主观对比：同一组 10 条测试语料（闲聊/查询/质疑各若干）flash vs pro + 新 prompt 的回复并排，pro 版明显更自然、无编造数字（人审）。
- 红线测试：问"帮我算算这碗面多少卡"→ 回复引导记录而不是自己算数；问无记录日期 → 明确说无记录。
- 谎称操作测试（复现 2026-07-03 案例）：在 discuss/chat 路径下说"记录成180kcal"、"帮我把那条删了"→ 回复不得出现"已更新/已删除"类字样，必须引导（T40 落地前引导说法，落地后此类输入应直接路由 modify）。
- 拒答测试：问编程/时事 → 仍礼貌拒答。
- token_usage 按 purpose=chat/query/discuss 记为 pro 模型；观察一周成本可接受（不达标可回退为"仅 discuss/chat 升 pro"）。
- 现有测试全绿。
