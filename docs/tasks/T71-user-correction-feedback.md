# T71 — 用户纠正回流食物库：改一次终身受益（估值层 E）

**状态**：⬜待决策（**不要直接开工**，见下"需要你拍板的问题"）

**目标**：用户手动覆盖热量后，纠正**只作用于那一条记录**，`food_standard.calories_100g` 永不更新。所以同一个错会无限重复——这正是 outoftoken 反复"改成850／改成900／饺子改为1100"的原因。让系统从纠正中学到"这个食物的热量密度不对"。

**依赖**：**硬依赖 T66**（三元组采集）。当前库里 6 条 `user_override` 只存了最终结果，推不出系统当时错了多少；没有 T66 的 `food_id / 系统值 / 用户值` 三元组，本任务无数据可用。
**关注文档**：`LEARNING_SPEC.md`（学习公式的唯一定义处，本任务要新增一类学习信号）、`FOOD_DB_SPEC.md`（权威分级，T70）、`CALORIE_ENGINE.md`。

## 背景（`npm run audit`，2026-07-27）

现有学习系统学了两件事：
- **食物身份**（T30 `upsertFoodAlias`）：这个用户说"葱花饼"指的是哪个条目
- **份量偏差**（T31 `UserBias`）：这个用户的"一碗"比 AI 估的大还是小

**唯独没学"这个食物的每 100g 热量估错了"。**

实测偏差（6 条覆盖，全部命中 AI 估算条目）：

| 食物 | 系统算 | 用户说 | 偏差 |
|---|---|---|---|
| 冰淇淋（自制） | 140 | 80 | **+75%** |
| 鸡胸肉面条 | 1190 | 900 | **+32%** |
| 炖鸡胸肉（冬瓜多肉少） | 70 | 120 | **−42%** |
| 炸鸡胸肉 | 150 | 185 | −19% |
| 莲菜肉饺子 | 1208 | 1100 | +10% |
| 炒面 | 833 | 850 | −2% |

**偏差两个方向都有**，不是能靠单一缩放系数修掉的系统性偏置。

另有一个结构性成因值得记下：`鸡胸肉面条` 那条 850g 是**连汤带面**，汤几乎不含热量，而 `kcal_100g × 克数` 是**均质线性模型**，对含汤/含水食物必然高估。用户手算 655、系统算 1190，差的就是汤的重量。**这类误差不是"估值不准"，是模型形状不对**——是否要引入"可食固体占比"之类的非线性口径，属于本任务需要决策的范围之一。

## 需要你拍板的问题（决定后再写实现细节）

**Q1：纠正的作用域是全局还是个人？**
- **全局**（改 `food_standard`）：一次纠正全体受益，但一个用户把"葱花饼"改成 180，会影响所有人；且 `FoodStandard` 无 user_id，天然全局。
- **个人**（新建 per-user 覆盖层）：安全、可解释，但每个用户都要自己纠一遍，冷启动无收益。
- **折中**：个人层立即生效；同一条目累计 N 个不同用户、方向一致时才提升为全局候选（走 T33 那套复核）。

**Q2：只回流 `is_estimated=true` 的条目，还是也允许改成分表条目？**
建议只回流估算条目（成分表是权威事实，不该被单个用户改），但需你确认。

**Q3：要不要引入非线性口径（含汤/含水占比）？**
做了能真正修掉汤面那类 +32% 偏差；不做则这类食物只能靠用户每次覆盖。成本不低（要改估算 prompt、schema、算账口径）。

**Q4：多少样本才够改？**
1 次就改（激进，易被误操作带偏）／ N 次同向才改（稳，但慢）／ 贝叶斯式加权（与 `LEARNING_SPEC` 的 `UserBias` 精神一致，推荐）。
